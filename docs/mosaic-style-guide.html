Mosaic Design System
One visual language across the Portal, the Planning Board, and the Comms Dashboard. Tokens live in mosaic-tokens.css — link that file in each app before its own stylesheet, then replace hardcoded values as you go.

The one rule

If you remember nothing else from this document, remember this.

Hue encodes type. Fill encodes status. Colour never encodes navigation, scope, or priority. Scope uses weight and size. Priority uses position.

This is why the three apps currently look unrelated: each invented its own colour meaning. Once hue means the same thing everywhere, a purple chip in the comms dashboard and a purple chip in the portal are the same kind of object, and the apps read as one product even before the layouts match.

Type colours

Three, and only three, on any calendar. They sit far apart on the colour wheel on purpose — earlier drafts used blue, purple and slate, which were nearly indistinguishable at chip size.

Each type needs four values, not one. The mid-tone hue is for borders and dots; the tint is for scheduled states; the solid is for done states, because the mid-tone fails contrast under white text at 10–11px; the deep is for text on tint.

Status treatments

Five states, applied on top of whichever type hue the item carries. Shown here on the comms amber — the same treatments apply to every hue.

Drafting Scheduled Sent Waiting on someone Off track
The dashed outline means a person is blocking this. It is the most useful signal on any of these screens, because it is the only state a human can clear. Reserve it for that and nothing else.

Scope, phase, campus and owner all want to be colours and none of them can be. There are only so many distinguishable hues, and type has already spent three of them. Everything else uses weight, position, or words.

Neutrals

Light and very slightly warm — blue is the lowest channel in every one, which is what keeps them from reading cold.

Grid lines are a separate, darker token from list separators. Calendar structure needs to be visible; list rows do not, and darkening those makes a list look like a spreadsheet.

Typography

Inter, three weights. Negative tracking throughout — -0.011em on body, -0.03em on large titles.

Banners and empty states

Read-only here. Creating and editing happens in the Comms dashboard, which stays the source of truth.
No attendance recorded. Submit attendance
Empty states say what is missing and how to fix it. A blank panel reads as broken; a sentence with a link reads as designed — and in the attendance case, it quietly drives submissions.

Detail views · three orderings

Any detail view — a campaign, an event, a send, a project — can be ordered three ways. The content is identical; the ordering decides what it's for. Pick one per audience and don't mix.

OrderingAnswersBest forUse in
By categoryWhat is this?Briefing someone, looking up a factComms item detail, reference screens
By timeWhat happens between now and then?Running a campaignPortal event page, PM campaign detail
By urgencyDoes anything need me?Checking in, approvingLeadership view of the same page
The important one is by time, and the reason is dependencies. Comms and tasks are usually two separate lists that both answer "what's left" — split apart, you can't see that a task due Aug 20 blocks a send scheduled for Aug 18. Merge them into one dated stream and the conflict is obvious. That's information a categorised layout structurally cannot show.

Blocker cards

Announcement email is waiting on Carlos
Sent for approval 2 days ago · scheduled to go out Aug 6
Metcalf artwork is due today
Saul · blocks the promo text on Aug 18
A blocker names the person and what it holds up. "Waiting for approval" is a status; "waiting on Carlos, blocks the Aug 6 send" is a blocker. Only the second one gets a card. And a card always carries an action — if there's nothing to do, it belongs in a list, not up here.

Retrofitting the two existing apps

In this order. Each step is visible on its own, so you can stop after any of them and the app still looks better rather than half-finished.

#ChangeWhy first
1Link mosaic-tokens.css, set the font to Inter with the tracking valuesA single shared typeface does more for perceived unity than everything else combined
2Replace greys with the neutral tokensCheap, global, and stops the three apps reading as three different eras
3Replace borders with --m-hairline and --m-gridFixes the two most common complaints at once: too heavy in lists, too faint in calendars
4Map statuses to the five treatmentsThe moment a purple chip means the same thing in both apps, they feel related
5Swap chips, buttons, and segmented controls for the m- classesInteraction surfaces are what people touch most
6Remove colour from scope, phase, campus and ownerFrees the palette so type colour actually reads
7Rebuild detail views on one of the three orderingsLast, because it is the only step that changes how the app works rather than how it looks

Which patterns each app adopts

AppTakesDetail views ordered by
PortalAll of it — it is the reference implementationTime, with urgency as the leadership variant
Planning BoardTimeline bars, scope weighting, status treatments, run-up spine, readiness strip, blocker cardsTime — a campaign detail is a run-up by definition
Comms DashboardCalendar cells, chips, status treatments, list rows, accordion sectionsCategory for a single send; urgency for the queue view
The planning board gets the most out of this. It already has a timeline view — adding the run-up spine to a campaign detail screen means the same object reads the same way whether you meet it in the portal or in the board itself.
Do not start by rebuilding layouts. Type, greys, lines and status colour get you most of the way, and none of them require touching how either app works.

Drop-in snippet

If you only copy one thing into the other two apps, copy this.

<link rel="stylesheet" href="/css/mosaic-tokens.css">
<link rel="stylesheet" href="/css/app.css">   <!-- your existing styles, second -->

<!-- then, in the app's own CSS, stop hardcoding -->
.some-existing-class{
  font-family: var(--m-font);
  letter-spacing: var(--m-tracking);
  color: var(--m-text);
  background: var(--m-surface);
  border: 1px solid var(--m-hairline);
  border-radius: var(--m-r-card);
}

<!-- a comms item, whatever its status name is in your data -->
<span class="m-item m-item--attention"
      style="--h:var(--m-comms); --t:var(--m-comms-t);
             --d:var(--m-comms-d); --s:var(--m-comms-s)">
  Metcalf announcement
</span>
